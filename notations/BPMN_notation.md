# Нотация BPMN 2.0 (Business Process Model and Notation)

> Источник: **OMG Document Number: formal/2011-01-03 — "Business Process Model and Notation (BPMN), Version 2.0"**, Object Management Group, January 2011. Документ: `formal-11-01-03.pdf`.

Настоящий файл — структурированное изложение материала спецификации, ориентированное на нотацию (графический язык) и базовые модельные конструкции BPMN 2.0. Часть, относящаяся к XML-схемам, метамоделям BPMN DI и отображению в WS-BPEL 2.0, в полном объёме не воспроизводится; ссылки на соответствующие главы исходной спецификации сохранены.

---

## 1. Общие сведения

### 1.1 Назначение BPMN

BPMN — стандартизированная нотация и модель бизнес-процессов с форматом обмена, обеспечивающим переносимость определений процессов между различными инструментами. Цель — позволить пользователям описать процесс в одной среде и использовать определение в другой.

BPMN 2.0 расширяет возможности версии 1.2:

- формализованы исполнительские (execution) семантики для всех элементов BPMN;
- введён механизм расширений как для модели процесса, так и для графических элементов;
- уточнены композиция и корреляция событий;
- расширено описание человеческих взаимодействий;
- определена модель **хореографии**;
- устранены известные неоднозначности и противоречия BPMN 1.2.

BPMN покрывает понятия моделирования, применимые к бизнес-процессам. Вне рамок спецификации:

- модели организации и ресурсов;
- функциональные декомпозиции;
- модели данных и информации;
- стратегические модели;
- модели бизнес-правил.

BPMN не является языком потоков данных; вопросы операционного симулирования, мониторинга и развертывания процессов в рамках стандарта не рассматриваются. BPMN 2.0 может отображаться в платформо-зависимые языки исполнения (например, WS-BPEL 2.0 — отображение приведено в гл. 14 исходной спецификации).

Спецификация использует другие стандарты для типов данных, выражений и операций сервисов: **XML Schema**, **XPath**, **WSDL**.

### 1.2 Виды конформности

BPMN 2.0 определяет несколько типов соответствия (Conformance):

1. **Process Modeling Conformance** — моделирование процессов.
2. **Process Execution Conformance** — исполнение процессов.
3. **BPEL Process Execution Conformance** — исполнение через WS-BPEL.
4. **Choreography Modeling Conformance** — моделирование хореографии.

## 2. Виды моделей BPMN

В рамках сквозной модели BPMN выделяют три типа суб-моделей:

1. **Процессы (Orchestration):**
   - **Private Non-executable** — частный (внутренний) непослолняемый процесс (документация поведения).
   - **Private Executable** — частный исполняемый процесс (со всеми деталями для исполнения).
   - **Public Process** — публичный процесс, представляющий взаимодействие частного процесса с внешними участниками; видна только активность, общающаяся с другими сторонами. В BPMN 1.2 назывался "abstract".
2. **Хореографии (Choreographies)** — описание ожидаемого поведения и контракта взаимодействия двух и более участников; "процедурный контракт".
3. **Коллаборации (Collaborations)** — взаимодействие нескольких бизнес-сущностей; коллаборация может включать процессы и/или хореографии. Отдельный вид взгляда на коллаборацию — **Conversation** (логически связанные обмены сообщениями вокруг бизнес-объектов).

### 2.1 Точка зрения (Diagram Point of View)

Одна и та же диаграмма может рассматриваться с разных точек зрения участников. Часть активностей для участника — внутренние, часть — внешние. На стадии исполнения это разделение важно, но сама диаграмма остаётся одной. BPMN не задаёт обязательного графического маркера для отображения точки зрения — это оставлено инструменту/моделеру.

### 2.2 Понятие токена

Для описания поведения процесса используется теоретическая концепция **токена**, проходящего по Sequence Flow и через элементы процесса. Start Event порождает токен, конечная точка — End Event — должна поглотить токен. Реализация токена в инструментах не обязательна. Токен **не** пересекает Message Flow — там передаётся сообщение.

## 3. Категории элементов BPMN

Графические элементы организованы в пять основных категорий:

1. **Flow Objects** — главные графические элементы, определяющие поведение процесса:
   - Events (события)
   - Activities (активности)
   - Gateways (шлюзы)
2. **Data** — данные:
   - Data Objects
   - Data Inputs
   - Data Outputs
   - Data Stores
3. **Connecting Objects** — соединительные объекты:
   - Sequence Flows
   - Message Flows
   - Associations
   - Data Associations
4. **Swimlanes** — дорожки:
   - Pools (пулы)
   - Lanes (дорожки внутри пула)
5. **Artifacts** — артефакты (стандартные):
   - Group
   - Text Annotation

Дополнительные артефакты могут добавляться моделером/инструментом.

## 4. Базовые элементы (Basic Modeling Elements)

| Элемент | Графика | Описание |
|---|---|---|
| **Event** | Окружность | "Случается" во время процесса/хореографии; имеет причину (trigger) и/или результат (result). Виды: **Start**, **Intermediate**, **End**. |
| **Activity** | Прямоугольник со скруглёнными углами | Работа, которую выполняет компания. Бывает атомарной (Task) или составной (Sub-Process). |
| **Gateway** | Ромб | Управляет ветвлением и слиянием Sequence Flow; внутренний маркер задаёт тип поведения. |
| **Sequence Flow** | Сплошная стрелка | Порядок выполнения активностей в процессе/хореографии. |
| **Message Flow** | Штриховая стрелка с открытой стрелкой и кружком в начале | Поток сообщений между двумя участниками (двумя пулами). |
| **Association** | Тонкая пунктирная линия | Связывает информацию и артефакты с элементами BPMN; стрелка может указывать направление. |
| **Pool** | Большой прямоугольник | Графическое представление участника в коллаборации. Может быть содержательным или "чёрным ящиком". |
| **Lane** | Подразделение пула | Поддорожка внутри процесса (как правило, в пуле); используется для группировки активностей. |
| **Data Object** | Лист бумаги с загнутым углом | Сведения о данных, требуемых/производимых активностями. Возможны Data Object Collection, Data Input, Data Output. |
| **Message** | Конверт | Содержимое коммуникации между двумя участниками. |
| **Group** | Прямоугольник со штрихпунктирной границей | Группа графических элементов одной категории; не влияет на Sequence Flow. |
| **Text Annotation** | Открытая скобка с текстом | Произвольный текстовый комментарий, привязываемый ассоциацией. |

## 5. Расширенные элементы (Extended BPMN Modeling Elements)

### 5.1 События — измерение Flow

| Тип | Назначение |
|---|---|
| **Start Event** | Указывает, где запускается процесс/хореография. |
| **Intermediate Event** | Происходит между стартом и концом, влияет на поток, но не запускает и не завершает процесс. |
| **End Event** | Точка завершения пути процесса/хореографии. |

### 5.2 События — измерение Type (триггеры/результаты)

Возможные типы: **None, Message, Timer, Error, Cancel, Compensation, Conditional, Link, Signal, Multiple, Parallel Multiple, Terminate, Escalation**.

- События могут быть **catching** (ловят триггер) — обычно Start и часть Intermediate; маркеры — без заливки.
- **Throwing** (бросают результат) — End и часть Intermediate; маркеры — с тёмной заливкой.
- Некоторые события (например, прерывания активности) могут использоваться в **non-interrupting** режиме — граница пунктирная.

### 5.3 Активности

- **Task (атомарная)** — единичная работа, не разбиваемая дальше в рамках процесса.
- **Sub-Process (составная)** — составная активность, разворачиваемая в подпроцесс или подхореографию:
  - **Collapsed** — детали скрыты, отображается значок `+`;
  - **Expanded** — детали видны внутри границ. Sequence Flow не пересекает границу Sub-Process.
- **Call Activity** — вызов глобально определённого Task/Process; рисуется с толстой границей.
- **Event Sub-Process** — внутренний подпроцесс, инициируемый событием; граница пунктирная.
- **Transaction Sub-Process** — подпроцесс-транзакция; граница двойная.
- **Choreography Task** — атомарная активность хореографии (один или более обменов сообщениями между двумя участниками); отображается лентами участников + полосой имени задачи.

#### 5.3.1 Маркеры Task

- **Loop** — стандартный цикл (стрелка-петля).
- **Multi-Instance** — три вертикальные линии (если последовательно — повёрнуты на 90°).
- **Compensation** — пара левых треугольников (как кнопка "rewind").

Маркеры могут комбинироваться (Loop + Compensation, Multi-Instance + Compensation), отображаются по центру нижней части.

#### 5.3.2 Типы Task

- **Abstract Task** (был "None Task" в BPMN 1.2) — без специализации.
- **Service Task** — использует сервис (Web service или автоматизированное приложение); маркер сервиса в верхнем левом углу.
- **Send Task / Receive Task** — отправка/получение сообщения.
- **User Task** — выполняется человеком при поддержке системы.
- **Manual Task** — выполняется человеком без участия ИС.
- **Business Rule Task** — обращение к движку бизнес-правил.
- **Script Task** — выполняется скриптом, исполняемым движком.

### 5.4 Шлюзы (Gateways)

Внутренние маркеры ромба определяют тип:

| Тип шлюза | Маркер | Поведение |
|---|---|---|
| **Exclusive (XOR)** | пусто или `X` | Выбор одной альтернативы по условиям на исходящих Sequence Flow. |
| **Event-Based** | пятиугольник с пятигранной звёздочкой | Выбор по событию, которое произойдёт первым (обычно — приход сообщения, таймер и т.п.). Может стартовать новый экземпляр процесса. |
| **Parallel Event-Based** | пятиугольник со знаком `+` | Параллельный вариант Event-Based. Тоже может стартовать новый экземпляр. |
| **Inclusive (OR)** | круг внутри ромба | Один или несколько путей по условиям. |
| **Complex** | звёздочка | Сложные условия слияния/ветвления (например, "3 из 5"). |
| **Parallel (AND)** | плюс `+` | Безусловное расщепление и синхронизация параллельных путей. |

### 5.5 Виды Sequence Flow

- **Normal Flow** — путь, не начинающийся с Intermediate Event на границе активности.
- **Uncontrolled Flow** — поток без условий и без шлюзов; токен идёт сразу.
- **Conditional Flow** — sequence flow с условным выражением. Если выходит из активности, в начале — мини-ромб; если из шлюза — мини-ромба нет.
- **Default Flow** — путь "по умолчанию" из Data-based Exclusive или Inclusive шлюза, диагональная черта в начале.
- **Exception Flow** — поток, начинающийся с Intermediate Event на границе активности (исключения).
- **Compensation Association** — связь, инициируемая Compensation Intermediate Event при сбое транзакции или явном бросании Compensation; цель — Compensation Activity.

### 5.6 Связь и направление

- **Fork (AND-split)** — разделение на параллельные пути:
  - неуправляемое — несколько исходящих Sequence Flow из активности;
  - либо явный Parallel Gateway.
- **Join (AND-join, синхронизация)** — Parallel Gateway сливает параллельные пути.
- **Decision (Branching)** — шлюз, в котором поток ветвится; разные типы (Exclusive, Event-Based, Inclusive, Complex).
- **Merging** — обычно Exclusive Gateway, объединяющий альтернативы.

### 5.7 Данные

- **Data Object** — описывает данные, требуемые или производимые; может быть коллекцией.
- **Data Input / Data Output** — для процессов в целом.
- **Data Store** — постоянное хранилище данных, доступное за пределами одного экземпляра процесса.
- **Message** — содержимое коммуникации между участниками.

### 5.8 Дорожки

- **Pool** — представление участника в коллаборации; может быть "чёрным ящиком".
- **Lane** — поддорожка внутри пула (или процесса), вытянутая на всю длину; для группировки активностей по ответственным/категориям.

### 5.9 Артефакты

- **Group** — визуальная группировка элементов одной категории; не влияет на поток.
- **Text Annotation** — текстовая аннотация, прикрепляемая ассоциацией.

## 6. Виды диаграмм BPMN 2.0

С помощью BPMN 2.0 можно создавать диаграммы:

- High-level (необязательно исполняемых) активностей бизнес-процесса (но не функциональных декомпозиций);
- детализированный исполняемый бизнес-процесс;
- As-is (текущий) или to-be (целевой) процесс;
- Choreography — описание ожидаемого поведения двух и более бизнес-участников;
- детализированный частный процесс с взаимодействиями с внешними сущностями (или "чёрными ящиками");
- два и более детализированных исполняемых процесса с взаимодействиями;
- связь детализированного исполняемого процесса с хореографией;
- два и более публичных процесса;
- связь публичного процесса с хореографией;
- два и более исполняемых процесса, взаимодействующих через хореографию.

## 7. Текст, цвет, размер, линии (рекомендации)

- Метки (имя/атрибуты) могут размещаться внутри фигуры либо снаружи в любой ориентации.
- Заливки графических элементов могут быть белыми/прозрачными; допускается использовать цвет (например, для подсветки атрибутов), однако:
  - маркеры **throw**-событий должны иметь тёмную заливку;
  - ленты участников у Choreography Task / Sub-Choreography, не являющихся инициаторами, должны быть со светлой заливкой.
- Размеры flow-объектов и маркеров — на усмотрение моделера.
- Линии — обычно чёрные; цвет/стиль линий могут расширяться, но не должны конфликтовать с уже определёнными в BPMN. Стили линий **Sequence Flow**, **Message Flow** и **Text Association** изменять/дублировать запрещено.

## 8. Правила соединения объектов потока

Sequence Flow и Message Flow могут подключаться к любой стороне Flow-объекта (слева, справа, сверху, снизу). Рекомендуется выбирать единую ориентацию Sequence Flow (слева-направо или сверху-вниз) и направлять Message Flow под углом 90° к ним.

### 8.1 Sequence Flow — правила (резюме)

- Sequence Flow не пересекает границу пула.
- Sequence Flow не пересекает границу Sub-Process (если он развёрнут).
- Подробные таблицы соединений между Events / Activities / Gateways приведены в Table 7.3 спецификации.

### 8.2 Message Flow — правила (резюме)

- Message Flow обязательно соединяет **разные** пулы (нельзя соединить два объекта внутри одного пула).
- Может подключаться к границе пула или к flow-объектам внутри пула.

## 9. Расширяемость BPMN

BPMN 2.0 предоставляет механизм расширения стандартных элементов дополнительными атрибутами. Расширения могут быть **mandatory** (соответствующая реализация обязана их понимать) или **optional** (могут игнорироваться). Расширения не должны противоречить семантике стандартных элементов; "footprint" базовых flow-элементов (Events, Activities, Gateways) изменять нельзя.

## 10. Структура ядра (BPMN Core Structure)

Спецификация устроена слоями, каждый из которых надстраивается над нижестоящими. **Core (ядро)** содержит наиболее фундаментальные элементы и обязателен для всех типов соответствия:

- **Process**
- **Choreography**
- **Collaboration**

Ядро состоит из трёх подпакетов:

1. **Foundation** — фундаментальные конструкции (BaseElement, FlowElement, расширения и пр.).
2. **Service** — конструкции для моделирования сервисов и интерфейсов.
3. **Common** — классы, общие для Process, Choreography, Collaboration.

### 10.1 Infrastructure (инфраструктура)

- **Definitions** — внешний контейнер для всех элементов BPMN; задаёт пространство имён и видимость. Атрибуты: `name`, `targetNamespace`, `expressionLanguage` (по умолчанию `http://www.w3.org/1999/XPath`), `typeLanguage` (по умолчанию `http://www.w3.org/2001/XMLSchema`), `rootElements`, `diagrams`, `imports`, `extensions`, `relationships`, `exporter`, `exporterVersion`.
- **Import** — описание импорта внешних элементов (XML Schema 1.0, WSDL 2.0, BPMN 2.0). Атрибуты: `importType` (URI кодировки), `location`, `namespace`.

---

## 11. Коллаборация (Collaboration)

- **Pool** — графическое представление участника. Несколько пулов в коллаборации обмениваются Message Flow. Пул может быть "чёрным ящиком".
- **Participant** — модельная сущность участника (PartnerEntity или PartnerRole).
- **Message Flow** — поток сообщений между двумя пулами.
- **Conversation** — особое представление коллаборации: гексагон, объединяющий логически связанные обмены сообщениями (например, вокруг бизнес-объекта "Order"). Пулы в Conversation, как правило, не содержат процесс, а хореография не размещается между ними.

## 12. Процесс (Process)

### 12.1 Базовые понятия

- Процесс — последовательность работ, представленная Flow-объектами и соединителями.
- Три вида процессов: **Private Non-executable**, **Private Executable**, **Public**.
- Процесс может ссылаться на **definitional Collaboration**, описывающую участников, с которыми взаимодействует данный процесс.

### 12.2 Активности

- Все активности — потомки абстрактного класса **Activity** (наследник `FlowElement`).
- Атрибуты активности: `isForCompensation`, `loopCharacteristics`, `resources`, `default` (Sequence Flow по умолчанию), `ioSpecification`, `properties`, `boundaryEventRefs`, `dataInputAssociations`, `dataOutputAssociations`, `startQuantity`, `completionQuantity`.
- Активность имеет состояние (`state`), описанное в "The Lifecycle of a BPMN Activity" (Section 13.2.2).
- Активности могут быть источником/целью Sequence Flow (несколько входящих и исходящих допускаются).
- Если активность не имеет входящего Sequence Flow, она инициализируется при инициализации процесса (исключения — Compensation Activity и Event Sub-Process).
- Активности могут иметь Message Flow (через Pool-границы).

### 12.3 Назначение ресурсов

- **ResourceRole** — роль ресурса; задаётся ссылкой `resourceRef` на ресурс или через выражение `resourceAssignmentExpression`. Возможны привязки параметров (`resourceParameterBindings`).
- **Performer** — конкретная роль исполнителя (человек, группа, организация).
- Параметры ресурса передаются через выражения — `ResourceParameterBinding`.

### 12.4 Task — атомарная активность

Прямоугольник со скруглёнными углами и тонкой границей. Спец. границы:

- толстая — **Call Activity**;
- пунктирная — **Event Sub-Process**;
- двойная — **Transaction Sub-Process**.

Маркеры: Loop / Multi-Instance / Compensation, могут комбинироваться.

#### Подтипы Task:

- **Service Task** — сервисный (Web-сервис/приложение); один input set, не более одного output set; маркер сервиса.
- **Send Task** — отправка сообщения участнику (маркер сообщения с заливкой).
- **Receive Task** — получение сообщения от участника (без заливки).
- **User Task** — задача, выполняемая человеком в поддержку ИС.
- **Manual Task** — выполняется человеком без ИС.
- **Business Rule Task** — обращение к bru-движку.
- **Script Task** — скрипт, выполняемый движком процесса.

### 12.5 Sub-Process

Разворачивается в собственный процесс. Sequence Flow не пересекает границу Sub-Process.

- **Embedded** Sub-Process — внутренний.
- **Reusable / Call Activity** — вызов глобально определённого Process / Task.
- **Event Sub-Process** — стартует внутренним событием, граница — пунктирная.
- **Transaction** Sub-Process — транзакционный, двойная граница; имеет специальную семантику commit/rollback и обработку ошибок.

### 12.6 События в процессе

Три категории — **Start**, **Intermediate**, **End**. Для процесса верхнего уровня доступны Start-триггеры: **None**, **Message**, **Timer**, **Conditional**, **Signal**, **Multiple**, **Parallel Multiple**.

Для **Sub-Process** допустим только **None Start Event** (поскольку триггер — токен из родительского процесса).

Для **Event Sub-Process** допустимы Start-триггеры: **Message**, **Timer**, **Escalation**, **Error**, **Compensation**, **Conditional**, **Signal**, **Multiple**, **Parallel Multiple**. Возможны interrupting (сплошная граница) и non-interrupting (пунктирная граница) варианты.

#### Стратегии передачи триггеров:

- **publication** — сообщение/сигнал доступен любым catch-событиям в области публикации; для Message используется correlation для идентификации экземпляра.
- **direct resolution** — через сигнал в текущей области.
- **propagation** — Error и Escalation распространяются вверх до ближайшей охватывающей области, перехватывающей этот триггер. Error — критическая ошибка, прерывает выполнение; Escalation — некритическая, выполнение продолжается.
- **cancellation** — прерывание всех активностей в подпроцессе; для транзакции — откат.
- **compensation** — вызов compensation handler для успешно завершённых активностей.

#### Носители данных в событиях:

- Catch Event — `dataOutputAssociations` распределяют данные сигнала в данные процесса.
- Throw Event — `dataInputAssociations` собирают данные процесса в данные сигнала.

### 12.7 Шлюзы (Gateway): подробнее

- **Exclusive (XOR)** — single-out на основе выражений, single-in для merge.
- **Event-Based** — выбор по событию (часто Receive Message); поведение "первое сработавшее"; парный Parallel Event-Based ждёт все.
- **Inclusive (OR)** — комбинация альтернатив, по условиям.
- **Complex** — нестандартные условия (например, M из N).
- **Parallel (AND)** — безусловный fork/join.

Шлюзы могут стартовать новый экземпляр процесса (Event-Based и Parallel Event-Based в начале процесса).

### 12.8 Items and Data

- **ItemDefinition** — описание типа данных (с указанием typeLanguage).
- **DataObject / DataObjectReference / DataState** — состояние и ссылки между объектами данных.
- **DataInput / DataOutput / DataInputAssociation / DataOutputAssociation** — для входа/выхода активности или процесса.
- **DataStore / DataStoreReference** — постоянное хранилище.
- **Property** — свойства, привязываемые к процессу/активности.

### 12.9 Compensation

Компенсация — отмена эффекта успешно завершённой активности. Маркер активности — пара треугольников; поток компенсации — Compensation Association с целью на компенсирующую активность; запускается Compensation Intermediate Event (catch на границе) или throw Compensation End/Intermediate.

### 12.10 Lanes

**Lane** — поддорожка внутри процесса/пула, вытянутая на всю его длину. Для категоризации активностей по ответственным или функциям.

### 12.11 Process Instances, Unmodeled Activities, Public Processes

- Каждый запуск процесса создаёт **instance**.
- Активности, не отображённые в модели, считаются "unmodeled" и не управляются движком.
- Публичный процесс показывает только взаимодействия с внешним миром.

### 12.12 Auditing и Monitoring

Атрибуты `auditing` и `monitoring` процесса/активности предусмотрены для интеграции с внешними системами аудита и мониторинга.

## 13. Хореография (Choreography)

Хореография — определение ожидаемого поведения нескольких участников. В отличие от обычного процесса, хореография существует **между** пулами; в ней нет центрального контролёра.

### 13.1 Базовые понятия

- **Choreography Task** — атомарная активность хореографии (один или более обменов сообщениями), вовлекает 2 участников. Графически — Task-фигура с лентами участников и полосой имени.
- **Sub-Choreography** — составная активность хореографии (collapsed/expanded).
- **Initiating participant** — участник-инициатор обмена; отображается без светлой заливки. Не-инициаторы — со светлой заливкой.

### 13.2 Использование общих элементов BPMN

Хореография использует Messages, Message Flows, Participants, Sequence Flows, Artifacts, Correlations, Expressions, Services, События, Шлюзы — со специфической семантикой.

### 13.3 События и шлюзы в хореографии

- Событийно-управляемое поведение хореографии описывается каталогом событий, аналогичным процессному, но с особыми правилами (например, Start-Event Choreography должен соответствовать message exchange).
- Шлюзы — те же типы (Exclusive, Inclusive, Parallel и др.); семантика — выбор/синхронизация в сценарии взаимодействия.

### 13.4 Хореография внутри коллаборации

Хореография может размещаться **между пулами** коллаборации и "разрезать" Message Flow между ними, выступая в роли описанного контракта.

## 17. Памятка для практика

- **Имя задачи** — глагольная фраза.
- **Pool — участник, Lane — категория**. Sequence Flow — внутри пула; Message Flow — между пулами.
- **Старт и конец процесса** — события (None Start/End, либо специализированные).
- **Развилки** — Gateway, тип определяется внутренним маркером ромба.
- **Параллельность** — Parallel Gateway (или несколько исходящих Sequence Flow без условий); синхронизация — также Parallel Gateway.
- **Условия** — на Sequence Flow или внутри шлюзов; для Default Flow — диагональная черта в начале.
- **Прерывания и исключения** — Intermediate Event на границе активности.
- **Компенсация** — отдельный путь через Compensation Association.
- **Хореография** — там, где нет владельца процесса; описывает контракт между участниками.
