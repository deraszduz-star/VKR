# Нотация IDEF0 (Integration DEFinition for Function Modeling)

> Источник: **FIPS PUB 183 — Draft Federal Information Processing Standards Publication 183, December 21, 1993, "Announcing the Standard for Integration Definition for Function Modeling (IDEF0)"**, National Institute of Standards and Technology (NIST). Документ: `idef0.pdf`.

Настоящий файл представляет собой структурированный конспект нормативной части стандарта (Sections 1–3) и ключевых положений информативных приложений (Annexes A–D) в применении к моделированию функций систем и предприятий.

---

## 1. Общие сведения

### 1.1 Что такое IDEF0

**IDEF0 (Integration DEFinition language 0)** — методика функционального моделирования, основанная на **SADT** (Structured Analysis and Design Technique) Дугласа Т. Росса (SofTech, Inc.). Стандарт описывает:

- графический язык моделирования (синтаксис и семантику);
- набор правил и техник построения структурированных графических представлений системы или предметной области;
- методологию разработки моделей, включая сбор данных, построение диаграмм, циклы рецензирования и документирование.

Стандарт принят в качестве Federal Information Processing Standard (FIPS 183) и базируется на руководстве "ICAM Architecture Part II, Volume IV — Function Modeling Manual (IDEF0)", выпущенном ВВС США в июне 1981 г. в рамках программы Integrated Computer-Aided Manufacturing (ICAM).

Помимо IDEF0 семейство методик ICAM включает:

- **IDEF1** — информационное моделирование (структура и семантика данных);
- **IDEF1X** — расширение IDEF1, семантическое моделирование данных;
- **IDEF2** — динамическое моделирование (поведение системы во времени).

### 1.2 Назначение и область применения

IDEF0 применяют для:

1. Системного анализа и проектирования на всех уровнях — от целого предприятия до отдельной предметной области.
2. Создания справочной документации, согласованной с разработкой и пригодной для интеграции новых либо улучшения существующих систем.
3. Коммуникации между аналитиками, проектировщиками, пользователями и руководителями.
4. Достижения консенсуса в команде на основе общего понимания.
5. Управления крупными и сложными проектами через качественные показатели прогресса.
6. Использования модели как опорной архитектуры предприятия, информационного инжиниринга и управления ресурсами.

### 1.3 Характеристики языка

- **Универсальность** — пригоден для систем разного назначения, масштаба и сложности.
- **Строгость и точность** — обеспечивает корректные и пригодные к использованию модели.
- **Лаконичность** — облегчает понимание, коммуникацию, согласование и валидацию.
- **Концептуальность** — описывает функциональные требования независимо от физической или организационной реализации.
- **Гибкость** — поддерживает несколько фаз жизненного цикла проекта.
- **Независимость от инструментов** — может использоваться вместе с CASE-средствами, но не привязан к ним.

## 2. Базовая терминология (нормативный глоссарий)

| Термин | Определение |
|---|---|
| **A-0 Diagram** | Контекстная диаграмма с одним блоком — верхняя функция модели с её входами, управлениями, выходами, механизмами, формулировками точки зрения и цели. |
| **Arrow (стрелка)** | Направленная линия из одного или нескольких сегментов, моделирующая канал передачи данных/объектов от источника (без наконечника) к получателю (с наконечником). 4 класса: Input, Output, Control, Mechanism (включая Call). |
| **Arrow Label** | Существительное или именная группа, описывающая значение стрелки или её сегмента. |
| **Arrow Segment** | Отрезок, начинающийся/заканчивающийся на стороне блока, в точке ветвления (fork/join) или на границе диаграммы. |
| **Boundary Arrow** | Стрелка, у которой один из концов (источник или получатель) не подключён к блоку на диаграмме. |
| **Box (блок)** | Прямоугольник с именем и номером, представляющий функцию. |

| **Child Box / Child Diagram** | Блок на дочерней диаграмме / диаграмма, детализирующая родительский блок. |
| **Context** | Непосредственное окружение функции (или набора функций диаграммы). |
| **Context Diagram** | Диаграмма с узловым номером A-n (n ≥ 0), задающая контекст модели. Обязательна A-0; A-1, A-2 — опциональны. |
| **Control Arrow** | Стрелка управления — условия, необходимые для получения корректного результата. Заходит в блок сверху. |
| **Decomposition** | Разделение моделируемой функции на компоненты. |
| **Detail Reference Expression (DRE)** | Ссылка (узловой номер, C-номер, номер страницы) под нижним правым углом блока, указывающая на детализирующую его диаграмму. |

| **For Exposition Only (FEO) Diagram** | Иллюстративная диаграмма, не обязанная соответствовать правилам IDEF0; используется для пояснения. |

| **IDEF0 Model** | Графическое описание системы или предмета моделирования, разработанное с конкретной целью и с выбранной точки зрения; набор IDEF0-диаграмм с текстом и глоссарием. |

| **Squiggle** | Маленькая зигзагообразная линия, связывающая метку с конкретным сегментом стрелки или примечание с компонентом диаграммы. |
| **Text** | Общий текстовый комментарий к графической диаграмме. |
| **Title** | Глагол или глагольная фраза, описывающая всю функцию диаграммы; для дочерней диаграммы совпадает с именем родительского блока. |
| **Tunneled Arrow** | "Тоннелированная" стрелка — не подчиняется обычному требованию соответствия стрелкам родительской/дочерней диаграмм. |
| **Viewpoint** | Краткая формулировка перспективы (точки зрения) модели. |

## 3. Концепция модели

Модель — представление набора компонентов системы или предметной области, разработанное для понимания, анализа, улучшения или замены системы. Системы состоят из взаимодействующих частей (люди, информация, ПО, процессы, оборудование, продукты, сырьё), совместно выполняющих полезную функцию.

Модель IDEF0 описывает:

- **что** делает система,
- **что** ею управляет,
- **над чем** она работает,
- **какими средствами** выполняет функции,
- **что** производит.

Модель состоит из иерархии диаграмм, последовательно раскрывающих детали функций и их интерфейсов. Существуют три типа диаграмм:

1. **Графические** — основная составляющая, содержат блоки, стрелки и связи.
2. **Текстовые** — концентрированный обзор, поясняющий ключевые особенности.
3. **Глоссарные** — определения ключевых слов, фраз и аббревиатур.

## 4. Синтаксис

### 4.1 Блоки (Boxes)

Блок описывает функцию. Каждый блок:

- содержит имя (активный глагол или глагольная фраза, например, "Perform Inspection", "Develop Detail Design");
- имеет номер в правом нижнем внутреннем углу.

**Правила синтаксиса для блоков:**

1. Блоки имеют размер, достаточный для размещения имени.
2. Блоки прямоугольные, с прямыми углами.
3. Блоки рисуются сплошными линиями.

### 4.2 Стрелки (Arrows)

Стрелка состоит из одного или нескольких сегментов с наконечником на одном конце. Сегменты могут быть прямыми или скруглёнными (90°-дугами), могут разветвляться (fork) и сливаться (join).

> **Важно:** стрелки IDEF0 — *не* поток управления и *не* временная последовательность, как в традиционных flow-моделях. Они выражают данные/объекты-ограничения. Получающая функция ограничена доступными данными.

**Правила синтаксиса для стрелок:**

1. Изгибы выполняются только дугами 90°.
2. Сплошные линии (без штрихов).
3. Только горизонтальные/вертикальные сегменты, без диагоналей.
4. Концы стрелок касаются внешнего периметра блока, не пересекая его.
5. Стрелки крепятся к сторонам блока, не к углам.

### 4.3 Стороны блока и роли стрелок (ICOM)

Каждая сторона блока имеет фиксированный смысл:

```
                Control (управление)
                       │
                       ▼
                ┌─────────────┐
   Input ───►   │ FUNCTION    │ ───► Output
   (вход)       │  NAME       │      (выход)
                └─────────────┘
                  ▲          │
                  │          ▼
            Mechanism      Call
            (механизм)    (вызов)
```

| Сторона | Роль | Что выражает |
|---|---|---|
| Левая | **Input** | Данные/объекты, преобразуемые функцией в выходы. |
| Верхняя | **Control** | Условия, ограничения, регламенты — без чего функция не даст корректный результат. |
| Правая | **Output** | Результаты — данные/объекты, произведённые функцией. |
| Нижняя (вверх) | **Mechanism** | Средства выполнения функции (люди, инструменты, ИС). |
| Нижняя (вниз) | **Call** | Особая Mechanism-стрелка, перенаправляющая детализацию на другой блок (в этой же или другой модели). |

### 4.4 Семантические правила для блоков и стрелок

1. Блок именуется активным глаголом или глагольной фразой.
2. Каждая сторона блока имеет стандартное соответствие с типом стрелки:
   - вход — слева, управление — сверху, выход — справа;
   - не-Call механизм — снизу, направлена вверх;
   - Call-механизм — снизу, направлена вниз; метка содержит ссылку на детализирующий блок.
3. Сегменты стрелок (кроме Call) подписываются существительным/именной группой, если общая метка стрелки не покрывает их однозначно.
4. Связь между стрелкой и меткой обозначается **squiggle**, если связь не очевидна.
5. Метки стрелок не могут состоять только из слов: function, input, control, output, mechanism, call.

## 5. Диаграммы

### 5.1 Типы диаграмм

#### 5.1.1 Контекстная диаграмма верхнего уровня (A-0)

Каждая модель имеет обязательную диаграмму **A-0** ("A минус ноль") с единственным блоком, представляющим всю предметную область, и его граничными стрелками. На A-0 указываются:

- **Viewpoint (точка зрения)** — определяет, что "видно" внутри модели и под каким углом;
- **Purpose (цель)** — выражает причину создания модели и определяет её структуру.

A-0 задаёт область охвата (scope) и ориентацию модели. Имя блока и метки стрелок здесь являются общими.

#### 5.1.2 Дочерняя диаграмма (Child Diagram)

Получается декомпозицией функции. Содержит дочерние блоки и стрелки, раскрывающие детали родителя. Имеет ту же область охвата, что и родительский блок — это его "внутренность".

#### 5.1.3 Родительская диаграмма (Parent Diagram)

Содержит один или более блоков, имеющих дочерние диаграммы. Обычная (не контекстная) диаграмма одновременно является и родительской, и дочерней.

#### 5.1.4 Текст и глоссарий (Text and Glossary)

Текст даёт обзор диаграммы, подсвечивает особенности, потоки и связи. Не используется для дублирования значения блоков и стрелок. Глоссарий определяет аббревиатуры и ключевые слова.

#### 5.1.5 Диаграммы "For Exposition Only" (FEO)

Используются для дополнительных пояснений отдельных областей модели. Не обязаны соответствовать синтаксическим правилам IDEF0.

### 5.2 Особенности диаграмм

#### 5.2.1 Стрелки как ограничения (Arrows as Constraints)

Стрелка, соединяющая выход одного блока со входом/управлением/механизмом другого, выражает: для выполнения функции получатель *требует* (ограничен наличием) соответствующего выхода источника. Только на самых низких уровнях стрелки могут выражать поток или последовательность.

#### 5.2.2 Активизации блока (Activations)

Блок может выполнять разные части своей функции при разных сочетаниях входов и управлений, давая разные выходы — это разные **активизации** (activations).

#### 5.2.3 Параллельная работа (Concurrent Operation)

Несколько функций модели могут выполняться одновременно при выполнении ограничений. Один выход одного блока может удовлетворять часть или все потребности нескольких других блоков.

#### 5.2.4 Стрелки как "трубопроводы" (Pipelines)

Стрелки верхнего уровня имеют общие метки и подобны трубопроводам/каналам. На нижних уровнях метки конкретизируются. При ветвлении каждый сегмент может иметь более точную метку.

#### 5.2.5 Ветвление стрелок (Branching: Fork/Join)

- **Fork** — одна стрелка делится на несколько; может означать unbundling.
- **Join** — несколько стрелок сливаются; может означать bundling.

Если на сегменте нет специальной метки, по всем ветвям передаётся всё содержимое исходной стрелки.

#### 5.2.6 Соединения между блоками (Inter-Box Connections)

- Кроме A-0, графическая диаграмма содержит **минимум 3 и максимум 6 блоков**.
- Блоки обычно располагаются по диагонали ("лестницей") из верхнего левого угла в нижний правый.
- Любой выход может направляться на вход/управление/механизм любого другого блока, в том числе через fork.

#### 5.2.7 Граничные и внутренние стрелки

- **Internal arrow** — оба конца подключены к блокам.
- **Boundary arrow** — один конец свободен. На обычной диаграмме граничные стрелки соответствуют стрелкам родительского блока.

#### 5.2.8 ICOM-кодирование граничных стрелок

ICOM-коды связывают граничные стрелки дочерней диаграммы со стрелками родительского блока. У свободного конца граничной стрелки пишется буква **I/C/O/M** и номер позиции (нумерация слева направо или сверху вниз).

Например: `C3` — стрелка соответствует третьему управлению, входящему в родительский блок (счёт слева).

При смене уровня роль стрелки может меняться — например, control родителя может стать input для дочернего блока.

#### 5.2.9 Тоннелированные стрелки (Tunneled Arrows)

Записываются с круглыми скобками `(...)` у одного из концов:

- Скобки **у конца, соединённого с блоком** — данные/объекты не нужны для понимания на нижестоящих уровнях, и стрелка не должна показываться на дочерней диаграмме. ICOM-код у такой стрелки сохраняется.
- Скобки **у свободного конца** — данные/объекты не нужны на верхнем уровне, и стрелка не должна показываться на родительском блоке. ICOM-кода нет; место "другого конца" может быть указано в model note.

#### 5.2.10 Call Arrows (стрелки вызова)

Особый вид Mechanism-стрелки. Показывают, что у блока-вызывающего нет собственной дочерней диаграммы — он детализируется другим блоком (в этой же или другой модели). Стрелка вызова метится узловой ссылкой и номером вызываемого блока. Один блок может вызывать только один блок за активизацию (хотя возможен список альтернатив, выбираемый по условию из model note).

### 5.3 Правила синтаксиса диаграмм (сводно)

1. Контекстные диаграммы имеют узловые номера `A-n`, `n ≥ 0`.
2. Модель содержит диаграмму **A-0** ровно с одним блоком.
3. Номер этого блока на A-0 равен **0**.
4. Не-контекстная диаграмма содержит **3–6 блоков**.
5. Блоки нумеруются 1…6 в правом нижнем внутреннем углу, по порядку от верхнего левого к нижнему правому.
6. Каждый детализированный блок имеет DRE под правым нижним углом.
7. Стрелки рисуются только горизонтальными/вертикальными отрезками (без диагоналей).
8. У каждого блока обязательно ≥1 control и ≥1 output.
9. Блок имеет 0 или более input.
10. Блок имеет 0 или более не-call механизмов.
11. Блок имеет 0 или 1 call-стрелку.
12. **Обратные связи** оформляются:
    - control feedback — "вверх и через" (up and over);
    - input feedback — "вниз и под" (down and under);
    - mechanism feedback — "вниз и под".
13. Свободный конец граничной стрелки имеет ICOM-код или тоннелирование.
14. Граничные стрелки одного содержания должны объединяться через fork (или join — для одинаковых выходов), кроме случаев, когда это ухудшает читаемость диаграммы.
15. Имена блоков и метки стрелок не могут состоять только из слов: function, activity, process, input, output, control, mechanism.

### 5.4 Ссылочные выражения

#### 5.4.1 Box numbers

Блок единственного на A-0 имеет номер `0`. На остальных диаграммах — `1…6`. На основной диагонали нумерация идёт от верхнего левого к нижнему правому; off-diagonal-блоки нумеруются после, против часовой стрелки начиная с правого нижнего.

#### 5.4.2 Node numbers

Узловой номер блока образуется приписыванием его номера к узловому номеру диаграммы, например блок 2 на диаграмме A25 — это `A252`. Все номера в IDEF0 начинаются с заглавной латинской буквы (`A`).

Контекст: `A-0` — обязательная контекстная диаграмма с единственным блоком A0; необязательные более общие — `A-1`, `A-2`, … . Дочерние диаграммы образуют последовательность `A0 → A1, A2, …, A6 → A11, …, A66 → A111, …`.

#### 5.4.3 Node references

Узловая ссылка на диаграмму: `<сокращение модели>/<узловой номер диаграммы>`, например `QA/A312`. Возможны суффиксы `F` (FEO), `T` (text), `G` (glossary) и номер страницы, например `QA/A321F1`.

#### 5.4.4 Node Index и Node Tree

- **Node Index** — отступной "оглавляющий" список узлов с заголовками диаграмм или именами блоков.
- **Node Tree** — графическое дерево "родитель–потомок"; содержание совпадает с Node Index.

#### 5.4.5 Model Notes

Опциональные текстовые примечания, обозначаются числом в маленьком квадрате `n` или вертикальными "трубами" `|n|`. Нумеруются последовательно с 1 для каждой диаграммы. Применяются для информации, которая не укладывается в синтаксис блоков и стрелок.

#### 5.4.6 Эталонная нотация ссылок

| Запись | Смысл |
|---|---|
| `2I1` | Вход 1 блока 2. |
| `O2` | Граничная стрелка с ICOM-кодом O2. |
| `2O2 to 3C1` | Стрелка из выхода 2 блока 2 в управление 1 блока 3. |
| `I2 to 2I3 to 2O2 to (3C1 and 4C2)` | Цепь: граничный вход I2 → вход 3 блока 2 → активизация → выход 2 блока 2 → одновременно control 1 блока 3 и control 2 блока 4. |
| `A21.3C2` | На диаграмме A21 — управление 2 блока 3 (точка означает «смотри конкретно»). |
| `A42. 3` или `A42.|3|` | Model note 3 на диаграмме A42. |
| `A42.3` | Блок 3 на диаграмме A42. |
| `MFG/A42.1` | Блок 1 на диаграмме A42 модели MFG. |

## 6. Структура модели IDEF0

### 6.1 Описание модели

IDEF0 раскрывает деталь постепенно. Модель начинается единственным "верхним блоком" (`A0`) с граничными стрелками и сопровождающей точкой зрения и целью. На каждом следующем уровне родительский блок раскрывается дочерней диаграммой, и так до достижения нужного уровня детализации.

### 6.2 Контекстные диаграммы

- Минимальный контекст модели — обязательная **A-0**.
- Опциональная **A-1** даёт более широкий контекст: блок A0 занимает место одного из 1–6 блоков, остальные представляют внешнюю среду; A-0 при этом всё равно обязательна.
- A-0 не имеет ICOM-кодов и тоннелирования у свободных концов стрелок.

### 6.3 FEO, текст, глоссарий

В рамках модели возможны диаграммы FEO (для пояснения), текстовые блоки и глоссарии, ссылающиеся на узлы соответствующими суффиксами в node reference.

### 6.4 Имя модели

Полное имя — описание моделируемой темы; сокращение (например, `MFG`, `QA`) включается в node reference.

### 6.5 Правила оформления

Стандарт устанавливает рекомендации по компоновке диаграмм, размещению меток, выравниванию стрелок и т.п. (см. также Annex B стандарта).

## 7. Концепции и руководства (Annex A–C, конспективно)

### 7.1 Три ключевые концепции IDEF0

1. **Графика моделирования активности** — лаконичная "коробка-стрелка" семантика для функций и их интерфейсов.
2. **Постепенное раскрытие деталей (gradual exposition)** — иерархия диаграмм, где каждый уровень даёт ограниченную и управляемую долю информации, что облегчает понимание и согласование.
3. **Дисциплина командной работы (disciplined teamwork)** — формализованные роли (автор, рецензент, читатель), процедура IDEF Kit Cycle, бланки и журналы для управления версиями и комментариями.

### 7.2 Чтение диаграмм (Annex B.1)

Рекомендуемый порядок при изучении модели:

1. Прочитать Purpose и Viewpoint.
2. Изучить A-0 — самая общая картина.
3. Спускаться по дереву декомпозиции (A0, A1…, A11…), читая параллельно текстовые комментарии и глоссарий.
4. Для каждой диаграммы:
   - просмотреть блоки и их имена;
   - обратить внимание на потоки (входы/управления/выходы/механизмы);
   - проследить, как граничные стрелки соответствуют родительскому блоку через ICOM.
5. Помнить: стрелки выражают **ограничения**, не "как" и "когда" выполняется функция.

### 7.3 Создание диаграмм (Annex B.2)

Базовые шаги авторинга:

1. Выбрать **контекст, точку зрения и цель** модели.
2. Создать **контекстную диаграмму** (A-0).
3. Создать **верхнюю диаграмму** (A0).
4. Декомпозировать выбранные блоки в дочерние диаграммы.
5. Подготовить **сопроводительные материалы** (текст, FEO, глоссарий).
6. Выбрать следующий блок для детализации и повторить.

Деятельность автора: фаза сбора данных, фаза структурирования, фаза презентации, фаза взаимодействия с рецензентами.

### 7.4 Цикл рецензирования IDEF (IDEF Kit Cycle, Annex C)

- Стандартный документооборот ("kit") с обложкой, бланками "Author/Date/Project", "Reader Notes", "Status", "Reader/Date", "Context", "Used At", "Message", "Node", "Title", "Number".
- Роли: автор, рецензент-комментатор, читатель.
- Чёткие правила обмена комментариями и проведения ревизий.

### 7.5 Сбор данных (Annex B.3)

Включает интервью с экспертами, использование "interview kit" — структурированного инструментария вопросов и форм для сбора фактов о функциях и интерфейсах системы.

## 8. Памятка для практика

- **Имя блока — глагол.** Метка стрелки — существительное.
- **Каждая сторона блока — стандартная роль.** Вход слева, управление сверху, выход справа, механизм снизу.
- **Стрелки — это ограничения.** Не путать с потоком управления как в блок-схемах.
- **Размер диаграммы.** 3–6 блоков (кроме A-0). Если нужно больше — декомпозируйте.
- **Согласованность граничных стрелок.** Каждая стрелка дочерней диаграммы (кроме тоннелированных) должна соответствовать стрелке родительского блока — через ICOM-код.
- **Тоннелирование** — точечный механизм исключения детали с конкретного уровня.
- **Call Arrow** — "ссылка на детализацию", когда блок не разворачивается собственной дочерней диаграммой.
- **DRE под блоком** — обязательно при наличии детализации.
- **Цель и точка зрения** — лидеры структуры модели; смена точки зрения меняет содержание модели.
